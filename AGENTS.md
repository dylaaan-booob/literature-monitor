## Scope and product constraints

- Implement the MVP one bounded task at a time and preserve the end-to-end behavior defined in `SPEC.md`. A complete authorized release is one task that may contain several sequential operations in one conversation; internal steps are not default approval or stopping points.
- `list.md` is the portable local-first source of truth for configured Journals and Publishers. Only Journals drive literature discovery; Conferences remain excluded from discovery and unrelated sections retain their storage-preservation boundary.
- Keep discovery/retrieval journal-whitelist-first, with exactly one user/configuration-owned normalized valid ISSN-L as each configured Journal's durable identity. OpenAlex is the primary discovery provider; Crossref is the secondary discovery and bibliographic-evidence provider. Semantic Scholar is not part of the supported production retrieval pipeline. Global keyword-first discovery and publisher scraping remain excluded.
- Verify OpenAlex Source membership by identifiers first. OpenAlex `issn_l` and Source aliases are Provider evidence, never authority to silently replace configured identity; validate aliases individually so malformed values do not poison unrelated valid evidence. Valid Crossref ISSNs may supplement/corroborate transient retrieval evidence but cannot select or rewrite canonical ISSN-L. Reconcile ambiguous/conflicting evidence conservatively; Journal names, alternate titles, abbreviations, Publisher names and hostnames have no Journal identity, merge or veto authority. Follow §41's migration confirmation and Paper/Group compatibility gates; add no mandatory external ISSN Registry runtime Provider or persistent alias/reconciliation registry.
- Isolate provider failures so successful evidence from other providers, journals, or requests remains usable. Consolidate available provider evidence before local keyword filtering decides inclusion.
- Use normalized DOI as the only supported canonical work identity under `SPEC.md` §37. Provider records contribute metadata/provenance to one Paper per DOI; do not merge different DOIs or maintain persistent manifestation/version state. Preserve workspace-local UUIDs for durable Paper references and never invent missing metadata.
- Treat Paper Markdown as durable user-facing workflow state. Preserve human-controlled status, unknown frontmatter fields, notes, and other human-authored sections during reruns.
- Keep disposable caches and indexes reconstructible. Do not introduce a mandatory second source of truth for workflow state.
- Do not add features outside the current `SPEC.md` scope, including conference monitoring, publisher scraping, global keyword-first discovery, LLM ranking or summarization, an Obsidian plugin, or custom bibliographic Zotero ingestion. §42 authorizes Keep-driven batch import through the pinned Zotero Connector, with at most one active capture, transient per-invocation identity and guarded `kept → exported` only on attributable native parent-save confirmation. Historical `export_attempt` fields remain untouched user data; they do not block a new explicit retry after failure or restart. Normal v0.6.3 import requires no My Library enumeration, unique-parent reconciliation, `in_zotero` state or `zotero_key`; §40's requirements for those remain historical v0.6.1 behavior. Parent and PDF outcomes are separate under §42; PDF observation must not become custom downloading or attachment management. The v0.5.x Browser Companion, custom PDF acquisition/staging, Zotero-write path and credential/session orchestration remain retired. Do not add Zotero synchronization, deduplication, deletion, merging, Collection/Group/tag routing, concurrent saves, full batch history or a library mirror.
- §41 permits OpenAlex Journal/Publisher metadata resolution and user-managed manual Publisher Access URLs within the shared Settings persistence boundary. Publisher identity is the direct OpenAlex Publisher ID; names, hostnames and corporate lineage cannot merge Publishers. Those URLs remain manual shortcuts and are not Access Service identity or authentication evidence. §42 narrowly permits federated access preparation for the current Kept import set through verified application routes and actual navigation evidence, with manual IdP/MFA/challenge completion in normal Chrome. Distinguish IdP session, SP session, authentication and full-text entitlement; keep observations process-local and fall back to manual access when evidence is insufficient. Do not guess routes, scan all Publishers, automate credential entry, store credentials/Cookies/SAML secrets/browser sessions, extract sessions or restore retired publisher-specific acquisition adapters. Unaffected Journal/Publisher ownership and Settings safety remain under §41.
- Do not freeze programming language, package layout, CLI names, cache format, export format, or other non-blocking implementation details before the task that requires that decision.

## Engineering constraints

- Prefer the smallest clear implementation that satisfies the current `SPEC.md` acceptance criteria. Add dependencies, abstractions, retries, persistence, or compatibility layers only when a current requirement or observed failure justifies them.
- Follow §37's disposable-data boundary for older Paper and Provider-state schemas; do not add Paper schema migration/legacy repair or row-preserving Provider-state v1/v2 migration.
- Make metadata updates idempotent and isolate partial source failures so successful records remain usable.
- Keep machine-managed writes narrowly targeted and explicitly test preservation of user-managed Markdown content whenever that behavior is touched.
- Respect upstream licenses and notices. The Python `literature_monitor` package remains MIT, while Zotero Connector-derived browser source/build artifacts must remain a separate AGPL-compatible component with upstream copyright/license notices, exact revision provenance and a clear Literature Monitor patch boundary. Connector-derived code must not enter the Python wheel or runtime import graph. Do not copy code whose license is absent or incompatible with the repository's chosen licensing obligations.
- Do not perform unrelated refactors, opportunistic cleanup, or unrequested scope expansion. Refactor only when necessary for the current change, and keep it within that change's boundary.

## Verification and completion

- For behavior changes, add or update tests that exercise observable results and the relevant `SPEC.md` acceptance criteria. Use network-independent tests where practical; do not substitute mocks for the required end-to-end validation when the specification explicitly requires live behavior.
- Before declaring work complete, inspect the actual implementation relevant to the task, the complete task diff and applicable validation evidence, including relevant test output. Confirm the requested scope and preservation of human-managed state and MVP boundaries; this inspection does not require rerunning still-applicable checks.
- Report checks that actually ran and any remaining unverified behavior. A written plan, created file, passing syntax check, or successful isolated unit test is not evidence that the full workflow works.
